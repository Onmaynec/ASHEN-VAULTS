# GitHub Issues — правила ведения ASHEN VAULTS

Эта инструкция относится к репозиторию [Onmaynec/ASHEN-VAULTS](https://github.com/Onmaynec/ASHEN-VAULTS).

## Обязательная структура

Каждая задача содержит **проверяемое название**, описание проблемы/цели, конкретные чекбоксы, условия приёмки, зависимые Issues и соответствующие метки. Ошибка содержит *шаги воспроизведения*, *фактический/ожидаемый результат*, версию, seed и среду. Завершать Issue только после необходимой проверки; для C++/UE4 нельзя подменять проверку сборки наличием исходников.

### Приоритеты

| Метка | Когда ставить |
| --- | --- |
| `priority: critical` (P0) | Нельзя собрать/запустить игру, нельзя пройти забег, потеря данных |
| `priority: high` (P1) | Механика ломается, важная регрессия, обязательная подготовка следующей версии |
| `priority: medium` (P2) | Не блокирует текущую сборку, будущий крупный контент |
| `priority: low` (P3) | Косметика, необязательные улучшения |

### Типы

- `bug` — обнаруженный/подозреваемый конкретный дефект с воспроизведением или анализом кода; **указать уровень подтверждения**.
- `enhancement` — реализуемая новая функция.
- `type: testing` — сценарий QA/регрессионных проверок, ещё не подтверждённый прогон.
- `type: epic` — крупная задача с несколькими независимыми частями.
- `documentation` — недостающая или ошибочная документация.

### Подсистемы

`area: build`, `area: gameplay`, `area: combat`, `area: performance`,
`area: graphics`, `area: ui`, `area: worldgen`,
`area: world`, `area: balance`, `area: audio`,
`area: saves`, `area: networking`.

### Версии

`version: 0.4.0` — баг или проверка текущих исходников. 
`target: 0.5.0` / `target: 0.6.0` / `target: 0.7.0` — ориентир для будущей работы, **не обещание даты выпуска**.

### Жизненный цикл

1. **Перед началом разработки:** найти существующее Issue; если нет — создать с нужными метками и чекбоксами.
2. **При разработке:** упоминать `#номер` в сообщениях commit или PR; если Issue часть Epic — связать с Epic.
3. **После разработки:** обновить чекбоксы и перечислить конкретные коммиты.
4. **Закрывать:** только когда критерии реально выполнены. В PR можно указать `Fixes #номер` для автоматического закрытия при merge, но не закрывать при отсутствии проверки.
5. **Неподтверждённые проблемы:** явно писать «обнаружено статическим анализом, воспроизведение в UE4 не выполнено» вместо заявления об исправленном игровом баге.
